# 知识维护规范

本规范用于团队知识正文；不会自动修改数据仓库、生产 SQL、在线规则表或其他 Agent 的配置。

## 目录与知识类型

`knowledge/{project}/{topic}.md` 保存正文与元数据；`project` 用稳定标识，如 `collart_web`，跨项目使用 `shared`。业务项目增多时直接增加项目目录。

| kind | 内容 | 至少说明 |
|---|---|---|
| business | 业务知识 | 产品定位、用户/角色、核心使用场景、流程、商业模式、适用市场和有效期 |
| table | 表和字段 | 全限定表名、行粒度、主键、分区、更新频率、核心字段、上游和使用限制 |
| metric | 指标口径 | 业务问题、分子分母、身份去重、窗口、时区、过滤、单位、退款/测试数据处理 |
| event | 埋点 | 实际 UI 动作、事件名、触发时机、参数、去重、是否意味着成功、缺失阶段 |
| lineage | 血缘 | 上下游、关联键、基数、运行顺序、历史覆盖和证据 |
| sql | 可复用 SQL | 参数、来源、粒度、日期过滤、预期输出、验证方式；长 SQL 存同目录文件并链接 |
| quality | 数据问题 | 症状、范围、发现日期、证据、影响、绕行方式与修复后核验 |
| playbook | 分析方法 | 输入、选择口径的条件、分析步骤、输出证据与限制 |

没有事实依据的章节保留缺口；不要为了“完整”猜测字段、指标定义、日期或业务目标。

## 元数据

正文开头是 YAML frontmatter 的简化子集：每行一个键，值使用 JSON 字面量（字符串加双引号，数组单行，空值为 `null`）。可用 `scripts/kb.py new` 生成，避免手工遗漏字段。

| 字段 | 维护约定 |
|---|---|
| id | 全库唯一稳定 ID，不随标题修改；重复主题更新原文 |
| title / project / kind | 中文标题、稳定项目 ID、上表类型 |
| status | `draft` / `documented` / `verified` / `deprecated` |
| updated_at | 本条最后编辑日期；不能代替事实发生日期 |
| effective_from | 规则生效日期，不知道用 null；复杂有效区间写正文 |
| verified_at / verified_by | 实际核验日期和人员/团队标识；未核验为空 |
| owner | 负责口径的人或团队；未指定为空，不虚构审批人 |
| review_after | 建议下次复核日期；到期产生提醒，不自动变更状态 |
| sources | `provenance/sources.json` 中的来源 ID 列表 |
| tags | 业务词、全限定表名、字段名及常见别名，帮助检索 |
| supersedes | 被本条替代的旧条目 ID，旧条目保留历史范围 |
| verification_evidence | 包内验证说明文件的相对路径，仅 verified / deprecated 使用 |

`draft`：口述或推断已记录，证据未齐、存在冲突，或尚未确认定义。

`documented`：有可追溯文档依据，但未独立核验。导入旧文档默认属于这一类。

`verified`：已经按本条范围核验，必须填 owner、verified_by、verified_at、review_after 和 verification_evidence。验证报告应说明方法、查询/业务确认依据、范围及结论；不放真实用户明细。脚本只检查这些字段及文件存在，不代替审核证据。

`deprecated`：停止推荐用于新分析，保留旧范围与替代条目。核验后来失效时也应保存历史核验记录，并说明失效原因。

修改已核验条目的实质口径时降为 documented / draft，清空当前核验字段，历史核验记录保留在版本记录或证据文件中。仅修字词且不改变含义可保留状态，并在变更记录注明。

## 一次完整维护

1. 检索同项目、表名或指标 ID，找到已有正文；不要在不同项目重复维护同一物理表的完整定义。
2. 写入新事实，说明来源、生效日期、适用层和粒度。存在相反证据时保存双方与待确认项，不按文件时间戳强行覆盖。
3. 新增来源时，将允许共享的必要摘录放入 `provenance/excerpts/`，在 `sources.json` 登记 ID、原始资料相对路径、原始文件 SHA-256、摘录路径和 SHA-256、采集日期、原文定位。路径无需依赖作者电脑。
4. 来自业务口述、在线文档或查询的知识：先保存一份可共享的证据说明文件到团队管理的原始资料目录，再登记来源。注明原话或 URL、发生日期、范围、查询/确认方式，不能伪装成生产验证。没有可用证据时仍可保存 draft。
5. 若做过实际核验，记录验证方法及局限后才设 verified。收入和转化至少核对成功证据、时间窗、去重及口径；表状态至少核对 schema 与相关分区；业务规则可以由已记录的负责人确认建立依据。
6. 仅在影响关联指标、SQL、血缘或历史版本时同步相关条目。表结构与业务含义不同层次的冲突，需分别记录。
7. 运行 `python scripts/kb.py index`、`python scripts/kb.py check`，在 CHANGELOG 记录条目 ID、变化原因与验证情况。技术检查通过后按公司仓库流程共享。

来源 SHA-256 可用 `Get-FileHash -Algorithm SHA256` 或 Python hashlib 生成。摘录是证据快照，不要求同事能打开原始个人路径；原文发生变化后不要只刷新哈希，需要评估受影响知识并保留变化解释。

## 读取时如何处理不确定性

- documented 的定义可用作分析起点，报告注明“依据知识库资料”；当前表是否存在、分区是否刷新、固定零是否恢复等状态必须现场验证。
- 碰到 draft 中的冲突，先查与当前问题相关的 schema、实现或业务确认。允许继续不依赖该冲突的工作。
- verified 也有验证窗口，不能把历史数据质量验证解释为今天一定正常。
- 日期、币种、毛额/净额、退款、设备/账号、新老用户、当日成功/历史付费缺失时，先明确当前计算契约。
- SQL 与事件样例仅用于理解口径，不构成生产执行或在线编辑授权。

## 现有知识迁移安排

现有 `ai-knowledge` 作为迁移素材。首版摘录只覆盖明确选择的知识，未整体复制私人配置、内部用户名单或历史分析报告。原来的维护 Skill 和目录继续服务已有工作流。

同主题一旦进入本包，团队修订写到本包；原始资料有变更时用 source-check 追踪差异，避免双向自动覆盖。后续按项目迁移完整的表/指标/事件目录，并在旧入口明确替代关系，待团队确定后再改旧入口。
