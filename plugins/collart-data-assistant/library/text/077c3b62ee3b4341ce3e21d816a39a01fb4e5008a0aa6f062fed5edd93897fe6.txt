# 1 表说明

> 文档整理：2026-09-12；业务状态：documented；复核：reviewed_static。原业务日期见正文，本次未重新查询生产数据。


## 表定位
Firebase / GA4 导出到 BigQuery 的原子事件明细表。  
每行代表一次事件上报记录。  

**⚠️ 重要：此表 Web 端和 Android 端共用**，需通过 `app_info.id` 或 `platform` 字段区分项目数据。

该表同时包含：

- 顶层字段
- 嵌套参数字段
- 重复 RECORD 字段

属于 **半结构化事件日志表**。

## 项目数据区分

| 项目 | 过滤条件 |
|------|----------|
| Collart Web | `app_info.id IS NULL` |
| Collart Android | `app_info.id = 'free.ai.photo.generator.collart.ai'` |

**Android 端文档** → 见 `collart_android/tables/storytemplate-10a27.analytics_232977577.events_.md`


## 查询限制（很重要）
- 使用 `_TABLE_SUFFIX`过滤表
- 单次查询时间跨度不能超过 30 天，如果用户请求超过 30 天，需要经过批准
- **必须过滤项目**：Web 端使用 `app_info.id IS NULL`

原因：
- events_* 为高数据量日志表
- 查询时间跨度过大会导致扫描数据量过大

示例sql：：
 ```
SELECT
  PARSE_DATE('%Y%m%d', event_date) AS stats_date,
  COUNT(*) AS pv
FROM `storytemplate-10a27.analytics_232977577.events_*`
WHERE _TABLE_SUFFIX BETWEEN FORMAT_DATE('%Y%m%d', DATE_SUB(CURRENT_DATE(), INTERVAL 30 DAY))
AND FORMAT_DATE('%Y%m%d', CURRENT_DATE())
AND app_info.id IS NULL
AND event_name = 'page_view'
GROUP BY stats_date
 ```


## 行粒度
一行 = 一个事件
注意：

- 不是 session 粒度
- 不是用户粒度
- 如果 UNNEST items，会变成商品粒度
- 如果错误 UNNEST event_params，会导致行数膨胀

## 表名模式

events_YYYYMMDD，例如：events_20260107
实时表：events_intraday_YYYYMMDD

## 推荐使用场景:
- 分析用户行为路径
- 分析页面浏览 / 页面来源 / 页面转化
- 分析埋点触发情况
- 分析漏斗转化
- 分析留存行为
- 分析自定义点击事件

## 不推荐使用场景:
- 未定义指标口径时直接输出业务报表
- 不建议当作普通平铺表来直接 select 所有业务字段
- 未核对 purchase 逻辑时直接输出收入
- 不做参数提取就把它当成普通平铺表使用

## join规则:
-推荐join key:
- user_pseudo_id
join粒度: 事件粒度
join常见风险:
- 重复字段展开后导致行数膨胀
- event_params 参数提取错误
- 时区理解错误
	
## 事件字段说明：
-  做时间范围过滤时，一定要使用 `_TABLE_SUFFIX`
- `event_date`：事件日期，在该表中不用做分区过滤
- `event_timestamp`：事件发生/接收时间戳，微秒级
- 做精确时间分析时优先使用 `event_timestamp`

## 质量说明:
- 半结构化事件表
- 含重复 RECORD 字段
- 依赖参数字典配合使用
- event_date 和 event_timestamp 含义不同

## agent使用规则:
- 查询 events_* 时必须使用 _TABLE_SUFFIX 过滤表
- 查询时间跨度不能超过 30 天
- 查询 events_* 时必须加过滤条件 app_info.id IS NULL
- 先判断目标字段是在顶层字段，还是在 event_params 中
- 顶层字段可直接取值,`event_params` 中的参数需要按 `key` 提取, `user_properties` 中的属性需要按 `key` 提取
- 提取单个 event_params 参数时，优先使用标量子查询，不要无脑全量 UNNEST
- 不同 event_name 对应不同参数，不要假设所有事件都存在同一组参数
- event_timestamp 为微秒级时间戳，查询时使用 TIMESTAMP_MICROS 转换
- 做业务指标时优先使用已沉淀的指标定义，不要直接基于 events 表自由发挥

 
# 2. 核心字段说明

## 字段名：`event_date`
- 类型：STRING
- 字段角色：日期字段 
- 是否可 group by：是
- 业务含义：事件日期，格式通常为 `YYYYMMDD`
- 注意：适合做表分区过滤，不适合替代精确事件时间

## 字段名：`event_timestamp`
- 类型：INTEGER
- 字段角色：事件时间字段
- 是否可 group by：否
- 业务含义：事件时间戳，微秒级
- 注意：查询时通常需使用 `TIMESTAMP_MICROS(event_timestamp)` 转换为标准时间

## 字段名：`event_name`
- 类型：STRING
- 字段角色：事件类型字段 / 过滤字段 / 分析维度
- 是否可 group by：是
- 业务含义：事件名称，如 `page_view`、`session_start`、`purchase`
- 注意：不同 `event_name` 对应的参数集合可能不同

# 字段名：`event_params`
- 类型：REPEATED RECORD
- 字段角色：事件参数容器
- 是否可 group by：否
- 业务含义：存储事件相关参数及自定义埋点参数
- 注意：读取参数时需基于 `key` 提取对应 value；不要无脑 UNNEST 后直接聚合
- `page_location` 保存完整页面 URL，可能包含 `utm_source`、`utm_medium`、`utm_content`、`utm_campaign`、`utm_term`、`utm_id` 等查询参数。
- 从 `page_location` 提取 Campaign 时，推荐先用 `REGEXP_EXTRACT(page_location, r'(?i)[?&]utm_campaign=([^&#]*)')` 保留原始值，再在导出层执行 URL decode；不能直接用 `traffic_source.name` 替代 URL 中的 `utm_campaign`。

## 字段名：`user_pseudo_id`
- 类型：STRING
- 字段角色：用户标识字段 / 去重字段 / join key
- 是否可 group by：是
- 业务含义：匿名用户标识，常用于用户去重和行为串联
- 注意：不等于注册用户ID，在未登录状态此id经常会发生变化；但是大部分分析场景目前用的是这个id

## 字段名：`user_id`
- 类型：STRING
- 字段角色：用户标识字段 / 去重字段 / join key
- 是否可 group by：是
- 业务含义：业务用户ID，只有部分用户在登录collart之后再会有
- 注意：在关联用户粒度收入表（aidata2025.ods.orders）时，用的就是user_id; 

# 字段名：`user_properties`
- 类型：REPEATED RECORD
- 字段角色：用户属性容器
- 是否可 group by：否
- 业务含义：存储用户级属性
- 注意：属性取值也需基于 `key` 提取；部分属性更新有延迟或覆盖问题

# 字段名：`geo`
- 类型：RECORD
- 字段角色：地理维度容器
- 是否可 group by：否
- 业务含义：地理信息，经常用`geo.country`取用户国家

## 字段名：`device`
- 类型：RECORD
- 字段角色：设备维度容器
- 是否可 group by：否
- 业务含义：设备信息
- 业务含义：device.category设备信息，device.mobile_brand_name品牌名称，device.operating_system操作系统、device.language设备语言，browser浏览器
- 注意：相关信息已加工到新增用户表`aidata2025.ads_collart.ads_oper_user_new_collartweb_di`和活跃用户表`aidata2025.ads_collart.ads_oper_user_collartweb_di`中，大部分场景会用user_id关联用户表获取渠道信息，正常分析不会从此字段来取值

## 字段名：`traffic_source`
- 类型：RECORD
- 字段角色：渠道维度容器
- 是否可 group by：否
- 业务含义：渠道信息
- 常用子字段：`traffic_source.name`，表示 GA4 用户获取层记录的 Campaign 名称。
- `traffic_source.name` 与某次访问 `page_location` 中的 `utm_campaign` 不是同一层级字段，分析时应分别保留，避免把用户获取 Campaign 当成本次页面 URL 的 UTM Campaign。
- 注意：相关信息已加工到新增用户表`aidata2025.ads_collart.ads_oper_user_new_collartweb_di`和活跃用户表`aidata2025.ads_collart.ads_oper_user_collartweb_di`中，大部分场景会用user_id关联用户表获取渠道信息，正常分析不会从此字段来取值

## 字段名：`app_info`
- 类型：RECORD
- 字段角色：包体维度容器
- 是否可 group by：是
- 业务含义：package_name
- 注意：具体分析时应使用其子字段，不建议直接把整个 RECORD 当成字段使用；在使用本表时要注意过滤app_info is null

# 3 事件说明

## 事件：first_visit
含义：
用户首次访问网站时触发，用于识别新用户。

常见分析：
- 新用户数统计
- 新用户趋势分析
- 新用户来源分析

注意事项：
- 一般用于识别首次访问用户，不等于首次注册用户
- 若业务有注册逻辑，需和登录/注册事件结合分析

## 事件：page_view
含义：
用户浏览页面时触发的页面展示事件，是最基础的浏览行为事件。

常见分析：
- 页面 PV / UV
- 页面来源分析
- 页面路径分析
- 页面漏斗分析

注意事项：
- 页面相关字段通常用于页面级流量分析
- 若要分析落地页转化，需和后续点击/生成/付费事件结合

### 参数： `page_name`
类型：string_value
含义：页面名称


## 事件：navigation_click
含义：
用户点击网站导航栏功能入口时触发。

### 参数： `feature`
类型：string_value
含义：导航栏点击的功能入口标识
参数值：
- `explore`：探索页
- `video`：功能页
- `asset`：结果汇总
- `subscribe`：订阅页
- `profile`：个人资料
- `more`：更多
- `language`：切换语言
- `credit`：积分


## 事件：explore_page_show
含义：
探索页或内容页展示事件，表示用户进入探索内容模块。

常见分析：

注意事项：
- 若 `temp_page` 表示分页页码，可分析翻页深度
- `type` 和 `category` 可能存在枚举值不统一问题，需要参数字典维护

## 模板5：统计页面PV和UV

```sql
WITH base AS (
  SELECT
    PARSE_DATE('%Y%m%d', event_date) AS stats_date,
    user_pseudo_id,
    (
      SELECT ep.value.string_value
      FROM UNNEST(event_params) ep
      WHERE ep.key = 'page_location'
    ) AS page_location
  FROM `storytemplate-10a27.analytics_232977577.events_*`
  WHERE _TABLE_SUFFIX BETWEEN '20260101' AND '20260107'
    AND event_name = 'page_view'
	and app_info.id IS NULL
)
SELECT
  stats_date,
  page_location,
  COUNT(*) AS pv,
  COUNT(DISTINCT user_pseudo_id) AS uv
FROM base
GROUP BY stats_date, page_location
ORDER BY stats_date, pv DESC;
```

# 6. 完整业务逻辑与事件漏斗

## 6.1 用户使用路径
```
访问 → 登录 → 选择模板/功能 → 开始生成 → 生成成功 → 结果保存/分享 → 付费购买
```

## 6.2 核心事件漏斗

### 漏斗1：登录链路
```
login_show（登录弹窗展示）
    ↓
login_account_choose（选择登录方式）
    ↓
login_success（登录成功）
```
**关键参数**：`from`（触发场景）

### 漏斗2：生成链路（以图生视频为例）
```
用户操作层：
img2video_show（功能页展示）
    ↓
img2video_model_choose（选择模型）
    ↓
img2video_resolution_choose（选择分辨率）
    ↓
img2video_generate_click（点击生成）
    ↓
服务执行层：
ai_service_start（服务开始）
    ↓
ai_service_upload_start（上传开始）
    ↓
ai_service_upload_success（上传成功）
    ↓
ai_service_execute_start（执行开始）
    ↓
ai_service_execute_success（执行成功）
    ↓
ai_service_success（服务完成）
    ↓
结果交互层：
ai_result_download（下载结果）
ai_result_share（分享结果）
```

### 漏斗3：付费链路（订阅）
```
点数用完/触发付费 → vip_show（付费界面弹出）
    ↓
vip_subscribe（付费项目点击，潜在付费意愿）
    ↓
vip_subscribe_succeed（付费成功）
```

### 漏斗4：付费链路（点数包）
```
订阅用户每周赠送点数用完 → credit_pack_purchase（购买点数包）
```

**完整付费模式：**
```
新用户注册 → 赠送30点数 → 登录使用 → 点数用完 → 订阅（每周送点数）→ 点数用完 → 购买点数包
```

## 6.3 关键业务规则

| 规则 | 说明 |
|------|------|
| 免费点数 | 新用户注册赠送30点数 |
| 订阅权益 | 订阅后无限使用 + 每周赠送点数 |
| 付费点 | 订阅用户额外购买点数包 |
| 登录时机 | 先生成部分内容，触发登录弹窗（降低门槛） |

## 6.4 分析建议

1. **登录转化分析**：关注 `from` 参数，了解哪些场景触发登录最多
2. **生成成功率**：对比 `*_generate_click` 和 `ai_service_success`，定位流失环节
3. **付费转化分析**：跟踪从免费点数→订阅→点数包的转化路径
