# Collart Fashion 数仓任务审查与优化建议

审查日期：2026-09-09。结论基于本次实时读取的 Dataform 源码、发布编译结果、运行记录、BigQuery 元数据和只读对账，不沿用旧审计的状态判断。

## 结论

Fashion 已有较完整的「事件明细 → 用户日 → 维度汇总 → 日报 / 用户画像」体系，且接入了 Stripe 收入。主要问题不是缺表或任务运行失败，而是**跨产品收入不互斥、内部账号口径不统一、画像随时间老化、旧新链路并存，以及收入刷新带动事件链路重复计算**。

建议先修口径与数据可信度，再处理重复调度和扫描成本。暂不建议重建整套数仓，也不能简单把所有刷新窗口缩到 3 天。

本次没有修改任何云端表、SQLX、工作流或调度，也没有改动旧血缘项目；仅在本地生成源码快照、校验 SQL、查询结果和本报告。

- 下载 23 份源码 / 配置快照，读取 14 张核心表元数据，并补查共享收入表数据。
- 日粒度对账：2026-09-06～2026-09-08。收入交叉验证选择较成熟的 9 月 7 日。画像比较覆盖当前 73,820 个用户，按 9 月 8 日作为统计截至日。

## 2. 现有体系

| 模块 | 任务 / 表 | 当前职责 |
|---|---|---|
| 共享明细 | `h_dm_collart_web_user_event_di` → `aidata2025.dm.dm_collart_web_user_event_di` | 从 GA4 提取 Web 事件；按 URL 的 `studio\|fashion` 识别 Fashion；重刷 biz_date-3～biz_date，共 4 个日期 |
| 收入归属 | `fashion_user_revenue` → `ads_collart.ads_oper_user_revenue_collart_fashion_di` | Stripe 同一 user_id 的交易，匹配前后 10 分钟最近支付成功事件；仅保留归属 Fashion 的交易，汇总到用户日 |
| 收入汇总 | `fashion_revenue` → `ads_collart.ads_oper_revenue_collart_fashion_di` | Fashion 日收入 / 支付次数 |
| 用户日 | `ads_oper_user_active_di`、`fashion_active_revenue_enrichment` | 活跃、新增、渠道、留存、用户日收入；当前存在两个写入 active 的任务 |
| 用户画像 | `ads_oper_user_profile_df` | 首末次活跃、滚动活跃天数、流失、累计收入 / LTV |
| 基础汇总 | `ads_oper_basic_indicator_attr_di / country_di / daily_di / daily_compare_di` | 维度、国家、日报和指标比较 |
| 事件汇总 | `ads_oper_user_event_metric_di / ads_oper_event_metric_attr_di / country_di` | 用户日事件 PV / UV 及汇总；规则生成 SQLX，但运行的是已生成的固定 SQL |
| 旧版兼容 | `fashion_daily_metric` → `ads_collart.ads_oper_basic_metric_collart_fashion_di` | 旧日报新增、自然新增、留存、活跃和收入 |
| 初始化 | `create_fashion_tables` | 旧表初始化；观察窗口未发现运行 |
| 共享收入消费 | `h_ads_ad_sub_revenue_1h` → `aidata2025.ads.ads_ad_sub_revenue_1h` | 跨产品收入汇总，读取 Fashion 日收入，同时读取包含 Fashion 的 Stripe Web 总盘 |

表名未写项目 / dataset 的新版 Fashion 表均在 `aidata2025.ads_collartfashion`。该 dataset 当前 9 张表约 94.07 MB；共享 DM 约 29.47 GB。主要优化对象是计算与扫描，不是这 9 张小表的存储。

核心关系可以概括为：GA4 → 共享 DM → active / event_metric → 各层汇总；Stripe + 共享 DM → Fashion 用户日收入 → active / 画像 / 收入汇总。共享收入表又把 Web 总盘与 Fashion 子集合并，需要特别处理“父级与子集是否可加”。

## 3. 已确认问题：按优先级处理

### F01 — 优先级最高：Web 与 Fashion 收入在共享表中重叠

`h_ads_ad_sub_revenue_1h` 把 `app_name='collart_web'` 的 Stripe 收入计入 Web，随后 `UNION ALL` 追加 Fashion 日收入，没有从 Web 中剔除已归属 Fashion 的部分。

9 月 7 日只读对账结果：

| 项目 | USD |
|---|---:|
| Stripe Web 正收入、非 expired 总盘 | 1,842.572433 |
| 其中按现有规则匹配到 Fashion 的 2 笔交易 | 25.341137 |
| 共享表 Web 收入 | 1,842.572433 |
| 共享表额外追加 Fashion 收入 | 25.34 |

**确定影响：若把共享表中的 Web + Fashion 相加，会比这份 Stripe Web 总盘多算 $25.34。**这不是 Fashion 新版日表自身多算，而是跨产品汇总口径不互斥。若业务有意把 Web 作为父级总盘、Fashion 作为子集，需要显式标记为不可相加。

优化：建设交易粒度的统一 `product_leaf` 归属，一笔交易只落一个叶子产品；保留 `product_parent='collart_web'` 用于总盘分析。总盘和叶子产品分别提供视图，避免直接混在同一个可加字段中。不要只在两张日报间做金额减法替代交易归属。

证据：[共享收入源码](<{LOCAL_PATH}>)、[对账 SQL](<{LOCAL_PATH}>)、[结果](<{LOCAL_PATH}>)。

### F02 — P1：共享表把全部 Fashion 收入硬写为美国

共享收入源码使用 `'United States' AS country`。9 月 7 日共享表 Fashion 的 $25.34 全在美国，而 Fashion 用户日收入维度是：印尼 $6.995022、美国 $18.346115。

优化：先确定商业指标使用“交易账单国家”还是“支付事件国家 / 用户当日国家”，并在字段名与文档中区分；将有证据的国家随交易向下传递，未知保留 `unknown`。不可把缺失国家统一补成美国。本次比较证明共享表国家不是用户日国家，不能据此认定支付账单国家一定为印尼。

证据：[硬编码位置](<{LOCAL_PATH}>)、[用户日国家分布](<{LOCAL_PATH}>)。

### F03 — P1：内部账号只在收入链路排除，活跃 / 事件指标未统一排除

按当前配置中的 18 个内部 user_id 直接识别：

| 日期 | Fashion 内部事件行 | active 中内部用户日 | AI 成功 PV：当前日报 | AI 成功 PV：去除直接识别的内部事件 |
|---|---:|---:|---:|---:|
| 09-06 | 0 | 0 | 3 | 3 |
| 09-07 | 938 | 3 | 16 | 15 |
| 09-08 | 939 | 3 | 20 | 11 |

9 月 8 日的 20 次 Fashion 视频 AI 成功事件有 9 次来自内部账号，占 45%。这里是事件 PV，不是按 task_id 去重的任务数，也不是成功率。

优化：保留完整 DM，并增加统一内部账号 / 测试流量标识；所有业务 ADS 统一采用相同排除规则。收入、活跃、事件漏斗不能各自复制名单。对于匿名事件是否跟随已登录设备排除，单独制定带有效期的身份映射规则，不能永久封禁整个共享设备。

证据：[过滤核查 SQL](<{LOCAL_PATH}>)、[核查结果](<{LOCAL_PATH}>)。上述去除仅覆盖直接携带已知 user_id 的事件，并非完整匿名身份归并后的最终业务口径。

### F04 — P1：不再活跃的用户，画像滚动指标停止更新

`ads_oper_user_profile_df` 只选择近 3 个日期出现过的 `changed_users`，但 `current_active_days`、`current_is_churn_14d` 本身会随着日期变化，即使用户没有新增事件。

对 73,820 个画像逐用户重算，截至 9 月 8 日：

- 近 7 日活跃天数不一致：3,348 个用户；全部属于近 3 日未活跃用户。
- 近 14 日活跃天数不一致：4,446 个用户。
- 14 日流失标识不一致：4,278 个用户。
- 累计购买收入不一致：0 个用户；active 与 profile 均合计 $604.826050。

优化：把画像分成“事件驱动的长期属性”和“每天会变化的快照属性”。流失可以由 `last_active_date` 在查询时计算；活跃天数可用近 7 / 14 / 30 天的窄用户日表每天刷新，或同时处理新进入与移出滚动窗口的用户。历史收入修正也应将受影响用户加入变更集合。

证据：[changed_users 逻辑](<{LOCAL_PATH}>)、[完整对账](<{LOCAL_PATH}>)。

### F05 — P1：旧日报自然新增使用了错误渠道枚举

`fashion_daily_metric` 使用 `traffic_src_type='organic'`，上游当前自然流量枚举为 `nature`。9 月 6～8 日，上游及新版日报自然新增分别为 **70、87、91**，旧日报均为 **0**。

优化：兼容层统一映射 `nature → organic`，并增加跨层校验。确认旧日报消费者后，可让旧版直接读取新版日报，避免再次实现渠道、留存和收入逻辑。上述数值用于存储层对账，尚未按统一内部账号规则重算。

证据：[错误枚举](<{LOCAL_PATH}>)、[对账结果](<{LOCAL_PATH}>)。

### F06 — P1：旧日报缺上游依赖，已观察到读旧版本的运行顺序

`fashion_daily_metric` 读取基础指标 attr 表，却只声明依赖 `fashion_revenue`。

| 运行日 / 北京时间 | 旧日报运行 | attr 更新运行 | 观察结果 |
|---|---|---|---|
| 09-07 | 07:00:28～07:00:33 | 07:00:33～07:00:39 | 存在重叠 |
| 09-08 | 07:00:28～07:00:33 | 07:00:34～07:00:40 | 旧日报先完成 |
| 09-09 | 07:00:33～07:00:39 | 07:00:31～07:00:42 | 存在重叠 |

优化：补充真实读取依赖，或依赖唯一的新版日报最终输出；将读取快照与依赖图一起验收。当前最终 DAU 已对齐，不能把“存在调度竞态”直接等同于“最终表一直错”。

证据：[三次运行记录](<{LOCAL_PATH}>)。

### F07 — P1：已建字段中混入“尚未实现”的固定零值

- active 的 `is_subscribe`、`is_credit_pack`、购买次数、购点数等固定为 false / 0，而 `is_purchase` 来自支付 / 购点事件。
- 9 月 7 日存储口径下 `purchase_uv=14`，但 subscribe_uv / credit_pack_uv 都为 0；当天有 2 笔已归属 Stripe 交易、$25.341137 收入。14 个事件购买用户与 2 笔服务端交易不是同一口径，不能直接比较转化率或断言漏单。
- 收入只填 `purchase_revenue`，新订阅 / 续订 / 购点收入均固定 0，不能把这些字段用作真实商业结构。
- country 表的 `delivery` 固定为 `(0.0, 0, 0, 0)`；这只能证明未接入成本，不能证明没有投放，ROAS 不可据此计算。

优化：明确区分“业务真实为 0”和“尚未支持”。事件订阅按事件规则与 product_id 映射，服务端交易按订单类型分类；加入 `metric_status / coverage_start`。成本从规范 DWD 成本链路接入，并确认 campaign → Fashion 产品映射；映射未知保留 unavailable。不要使用硬编码 0 伪装完整指标。

证据：[active 固定值](<{LOCAL_PATH}>)、[成本固定值](<{LOCAL_PATH}>)。

### F08 — P2：多轮调度重复重算，收入补齐牵动整条事件链

9 月 6～9 日每天观察到主链约 07:00、08:00、08:31 各执行一轮。9 月 9 日的追溯结果：

| 时间 | 工作流 | Fashion 动作 | 行为 |
|---|---|---:|---|
| 07:00 | `daily_wf_am` | 12 | 显式目标列表；不包含 enrichment |
| 08:00 | `daily_wf_am` | 12 | 同一工作流再次运行；不包含 enrichment |
| 08:31 | `daily_revenue_am` | 13 | 从收入任务展开所有下游，包含 enrichment，也重跑 active / event_metric / profile |

工作流配置内可见 07:00 cron；08:00 与 08:31 的实际运行已验证，但外部触发器 / 人工来源未追溯，不能直接断言可关闭其中任意一轮。

| 处理对象 | 观察窗执行次数 | 非 SCRIPT 处理量 GB |
|---|---:|---:|
| 共享 Web / Fashion DM | 8 | 798.58 |
| Fashion active | 12 | 62.75 |
| Fashion profile | 12 | 7.24 |
| Fashion user_event_metric | 12 | 1.41 |
| Fashion 全部专属动作合计 | — | 72.54 |
| 跨产品共享小时收入任务 | 87 | 123.36 |

GB 使用十进制。只累计非 SCRIPT 作业以避免父子重复计数；共享 DM / 小时收入服务多个产品，不能把其全部资源算到 Fashion 头上。Fashion active 约占其专属处理字节的 **86.5%**。

优化顺序：

1. 明确原始事件及 Stripe 的就绪水位，区分首次产出、最终日报与补数，不按固定时间盲目重复全链。
2. 把事件用户日与用户日收入拆开。收入到齐时，只刷新受影响日期的收入结果及商业汇总，不重新扫描 31～45 天事件。
3. 事件指标不依赖未来留存，默认只处理发生变化的分区；迟到事件通过已变更分区清单触发重算。
4. active 的 D30 留存需要历史回补。保留完整留存观察窗，但用窄用户日活跃事实更新留存，避免每天三遍重扫宽 DM。
5. profile 从窄事实和增量首访维表计算，避免反复读取全历史宽 DM。
6. 对被多次引用的 DM 子查询先查看执行计划，按需要物化窄临时结果；不能认为写成 CTE 就一定只扫描一次。[BigQuery 官方优化说明](https://docs.cloud.google.com/bigquery/docs/best-practices-performance-compute)

上述为优化设计，尚未运行修改后 SQL 或实测节省比例。不要将减少两轮调度等同于固定节省三分之二费用。

证据：[工作流触发追溯](<{LOCAL_PATH}>)、[作业统计](<{LOCAL_PATH}>)。

## 4. 潜在风险与需要补充验证的事项

这些是源码证据支持的风险，不作为已发生的数据事故：

| 风险 | 当前证据 / 边界 | 建议 |
|---|---|---|
| 支付归属完全依赖前后 10 分钟客户端成功事件 | 无事件、续订、晚到、跨端交易可能无法归属；本次没有估算漏归属金额 | 保留交易明细、匹配方式、时间差、未匹配原因和规则版本；优先服务端 product / order 映射 |
| `first_fashion_succeed_date` 不是全历史首次 | MIN 仅在滑动支付事件窗口内计算 | 使用稳定的用户首次支付维表，或明确命名为窗口内首次 |
| 一个 active 表有两个写入任务 | active 已包含收入补齐，enrichment 再写一次；用户日 / 设备日粒度也不同 | 单一责任写入；在最终设备日粒度先聚合，增加 MERGE 源键唯一性断言 |
| 收入和旧日报 DELETE / INSERT 无事务包裹 | SQLX 可先清空目标分区再失败 | 使用事务或原子分区替换；不要把每次运行的 DDL 与日常业务计算混在一起 |
| 外部 Stripe 就绪状态未纳入明确依赖 | 核心 Fashion 表 08:31～08:32 更新，Stripe 表 09:00 又有更新 | 以分区数据就绪 / 更新时间水位驱动；仅凭整表 modified 时间不能证明某日收入不完整 |
| formal / intraday 合并无来源优先或去重 | 代码允许同日两类表；本次 09-06～08 元数据只看到正式表 | 保留源表、事件标识和优先级后去重；没有证据宣称本次已重复 |
| URL 识别产品较脆弱 | 本次未发现 Fashion 命名 / fashion_video 事件落入 Web，外部事件 page_location 也未缺失 | 服务端 product_id 优先，URL 作为回退；保存归属原因与规则版本 |
| 国家 NULL 被 country 汇总丢弃 | 代码有 `country IS NOT NULL`；近三天 active 无空国家 | 将未知国家保留为 unknown，并校验国家汇总与总表守恒 |
| 枚举、时区、首次日 / LTV 边界分散 | SQLX 注释仍有 Apple IAP 等复制痕迹，实际 Fashion 使用 Stripe | 对每个指标标注事件 / 订单口径、时区、起算日、成熟日与支持状态；用边界样例测试 |

## 5. 本次也验证了哪些正常结果

- 最近三次 07:00 运行中 Fashion 相关动作成功；观察窗口的 Fashion 专属动作没有查到失败作业。
- 9 月 6～8 日 active 的用户日键未发现重复；active → attr → country → 新版 daily 的 DAU / DNU 能对齐。
- 9 月 7 日 Fashion 用户日收入、active、attr、country、daily 均为 $25.341137；旧收入表为 $25.34，存在已知两位小数舍入。
- 新版 AI 事件明细与日报 PV 能对齐，但一致性不代表已排除内部账号。
- profile 累计收入与 active 一致；不能因为滚动画像字段过期就把全部画像字段判为不可用。

这些检查是存储层守恒校验，不是对真实支付全量、完整埋点覆盖或所有历史日期的背书。

## 6. 推荐落地顺序与验收

| 阶段 | 任务 | 最小验收条件 |
|---|---|---|
| 第一批：口径修复 | 确认 Web 父级 / Fashion 叶子定义；统一交易归属与国家；统一内部标识；修旧自然枚举与依赖 | 叶子产品交易唯一且金额可守恒；国家未知不补美国；18 个已知内部账号不进入业务指标；旧新自然新增一致；下游晚于上游提交 |
