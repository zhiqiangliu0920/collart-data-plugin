# Collart Android 加工链路与关联边界

适用：选择 Android 分析来源、解释加工关系和核对 JOIN 粒度。依据：原链路正文及其 2026-08-11 渠道规则；2026-05-21 导出关系另见 [历史加工来源](warehouse_sources.md)。本页为文档证据，未重新验证调度运行状态。

## 已登记加工链路

`GA4 events_* → DWD → dm_collart_android_user_event_di → active / user_event_metric / profile → attr / country / daily`

上述链路是层级概览，具体表的直接依赖以对应表字典和加工任务为准。指标列定义来自 Sheet 外表 `ads_dim_metric_rule`，生成器展开进 SQLX，调度不直接 JOIN 规则表。热指标读取已物化列；冷指标按规则扫 DM，Android 的过程入口与条件见 [规则查询方法](../../1company/analysis_playbooks/event_metric_from_rule.md)。

## 关联粒度

- 行为与付费：先按业务目的聚合事件与订单，再用可靠身份映射关联；多条事件直接 JOIN 多条订单会放大金额。收入来源按 [公司 ADS 红线](../../1company/analysis_playbooks/collart_ads_redlines.md) 选择，不把旧 `orders` 示例当作默认来源。
- 用户属性：原始 GA4 的 user_properties 是事件内参数集合；读取 key 与类型，不能把示意图中的名字当作可 JOIN 的独立物理表。
- 留存：建立每用户唯一的 cohort 起始日期，再关联活跃日期，按明确 N 日偏移计回访；日期范围与类型要求见 [留存定义](../indicators/retention.md)。

原文的无日期上界示例、直接事件×订单 JOIN 以及使用 `dau`、`dwd_payment` 等占位名的血缘图已退出推荐入口。未提供真实表标识的示意图不作为仓库事实。

## 渠道两层规则（原记录生效日 2026-08-11）

原登记链路：`dm_collart_android_user_event_di → ads_oper_user_active_di → ads_oper_user_profile_df / ads_oper_basic_indicator_attr_di / ads_oper_event_metric_attr_di`。

- 暴露 `traffic_src_type` 的 ADS 表同时维护 `traffic_src_platform`。
- type：`delivery` / `inhouse` / `kol` / `nature`；platform：`ga_delivery` / `fb_delivery` / `x_delivery` / `tt_delivery` / `other_delivery`，非投放沿用渠道性质。
- Instagram 归 `fb_delivery`；`sptt-` / `tt_official` 属于 kol，不归 `tt_delivery`。
- profile 取首个非空来源；历史存在 delivery 时按原规则优先 delivery。type/name/platform 必须来自同一来源行。

跨产品公共表见 [公司表关系](../../1company/tables/cross_product_tables.md)。
