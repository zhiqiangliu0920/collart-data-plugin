## 0. 成本侧首选表（2026-08-07 起）

`aidata2025.dws.dws_oper_asa_delivery_di`（数仓 `definitions/dws/daily/h_dws_oper_asa_delivery_di.sqlx`）已把下面这些坑全部内置，**成本侧一律优先用这张表**，不要再手写去重 / 汇率 / 残差：

| 已内置 | 说明 |
|---|---|
| 整行去重 | 主键 `event_date × campaign_id × adgroup_id × keyword_id × country`，无重复 |
| 币种 | 直接给 `cost_usd` 与 `cost_cny` 两列 |
| 无关键词投放 | `is_keyword_attributed = FALSE`，`keyword_id` / `keyword` 为 NULL（Max Conversion 类） |
| 多产品隔离 | 有 `package_name` / `app_name`（VidArt 用 bundle id 过滤） |
| 名称 | 自带 `campaign_name` / `adgroup_name` / `keyword` |

字段：`event_date, app_name, package_name, country(两位码), campaign_id, campaign_name, adgroup_id, adgroup_name, keyword, is_keyword_attributed, cost_cny, cost_usd, impressions, clicks, installs, keyword_id`。

数据起点 2026-05-19。实测 2026-05-19~08-06 共 80 天，花费与安装与 Apple campaign 报表 **逐日 diff = 0**。

⚠ 两个使用注意：
- `keyword_id` 于 2026-08-07 补入；**2026-07-01~07-06 有 18 行关键词花费缺 `keyword_id`**（07-07 起正常）。按 keyword 汇总时需 `IFNULL(keyword_id,'(no_keyword)')`，那 6 天会并入 `(no_keyword)` 桶（不重复计数，仅丢粒度）。
- join 用户侧前必须把 NULL 换成占位值，NULL 不参与 join。

下面第 3 节的币种、去重、多产品红线，仅在**直读 ODS / 老 DWS** 时才需要自己处理。

## 3. 核心口径

**花费币种（红线）**：ASA 账户币种是**人民币**，`local_spend` / `ods_apple_*_reports_1d.local_spend_currency = 'RMB'`（2026-05-27 起有值，此前 NULL，账户币种未变）。收入侧 `event_value_in_usd` 是美元，两者直接相除 ROI 会低 6.8 倍。换算：`SAFE_DIVIDE(local_spend, rate)`，rate 取 `aidata2025.dim.exchange_rate_days` 中 **`currency='CNY'`**（注意不是 `'RMB'`）、`stats_date` 为 STRING 需 `CAST(... AS DATE)`。汇率表更新到 T-1，当天需用最近一天汇率兜底，否则 `cost` 变 NULL 并在 SUM 中被静默跳过。⚠ 给汇率子查询加 `stats_date >= 'X'` 下限时，早于 X 的查询窗口会因 rate 为 NULL 而**静默丢行**。

**成本表是多产品混表（红线）**：`dws_oper_asa_keyword_collart_1d` 表名带 collart，但实际包含整个 ASA 账号下所有产品的关键词花费（Collart / RoomAI / RemoveBG / Imagix / Pixelance / 老 ST 包 / VidArt）。2026-07 起其他产品均已停投，**只查 7 月看不出问题**，但日期一旦拉到 2026-05 之前就会混入别的 App。必须按 campaign 过滤（`campaign_name LIKE 'VidArt%'`，或 inner join 已过滤的 `kw_map`）。`ods_apple_campaigns_reports_1d` 同理。

**成本去重（红线）**：`ods_apple_*_reports_1d` 自 2026-05 起产生整行重复（月度重复系数 2.0~9.4，花费虚高 2.0~2.6 倍）。必须按 (日期, adgroup_id, keyword_id, country_region) 用 `ROW_NUMBER() ... ORDER BY local_spend DESC` 取**整行**，不可分列取 MAX（Apple 有重报，会造成指标跨行拼接）。去重后 campaign 级安装数与 GA4 Apple 归因用户数逐日吻合，可作为校验。

**GA4 表通配符（红线）**：`_TABLE_SUFFIX >= 'YYYYMMDD'` 是字符串比较，`intraday_20260730` 的首字符 `i` 大于数字，**会把 `events_intraday_*` 一并匹配进来**，导致当天数据与次日转正的 `events_*` 重复计入。必须写成 `BETWEEN 'YYYYMMDD' AND FORMAT_DATE('%Y%m%d', CURRENT_DATE())`。

**归因属性不可按天展开（红线）**：`keywordID` / `campaignID` 只挂在部分事件上，若按 (event_date, user, keywordID) 去重再按 user join，每个用户会额外产生一条 `keyword_id = NULL` 的行，归因用户同时落进「真 keyword」和「NULL」两个桶，收入双算（实测 2026-07 虚高 32%）。正确做法：`MAX(...) ... GROUP BY user_pseudo_id`，一个用户一行。另外 NULL 无法参与 join，需 `IFNULL(...,'(no_keyword)')` 占位。

**归因**：三级兜底 `user_properties.campaignID/keywordID` → `firebase_campaign` 事件参数 `campaign`/`term` → `traffic_source.name`（`source='Apple'`）。归因属性**不挂在 first_open 上**，需对用户全生命周期取值再回填首开日。GA4 里 keywordID / campaignID 的取值与 `dim_collart_asa_keyword_info` 的 id 完全一致。

**数仓落地（2026-08-12）**：上述三级兜底已写入 `dm.dm_collart_ios_user_event_di.traffic_src.campaign_id/keyword_id`；`ads_oper_user_active_di` 在当日出现 delivery/ASA 时优先取投放快照，避免被末次 nature 冲掉。用户侧 ASA SQL 可优先读 active/profile，不必再扫 GA4。注意：`dwd_oper_user_properties_di` / `event_params` 对 VidArt 自 **2026-07-26** 才有数据，此前 keyword 只能靠后续回填，campaign 靠 Apple+数字 `traffic_src_name` 兜底。

**归因起点 2026-07-20**：ASA 从 2026-05-18 起投，但 05-18~07-19 无任何用户级归因信号，该区间只能出成本侧指标。

**新增用户**：GA4 `first_open` 去重 `user_pseudo_id`（每用户仅一条）。

**收入**：`in_app_purchase.event_value_in_usd` 为毛收入（美元）；净收入 = 订阅 ×0.85 + 点数包 ×0.70（`LOWER(product_id) LIKE '%pack%'` 判定点数包）。`vip_subscribe_succeed` 无金额字段，只能计数。

**无关键词 campaign**：Max Conversion 类自动投放无关键词报表（7 月占花费 34%），需用 campaign 合计减关键词合计补 `keyword_id='(no_keyword)'` 行，否则漏计。

**国家**：ASA `country_region` = 两位码 = `dim_country_info.country_name_3`；GA4 `geo.country` = 英文全称 = `country_name`。约 6% 归因用户所在国家当天无 Apple 花费报表，需用 UNION 骨架保底避免丢收入。
